### 3.1 对应 2.1：选题来源与问题陈述

本实验围绕“AI需求歧义审查器”展开。项目目标是帮助课程作业或软件项目参与者在开发前检查需求文本中的模糊表达、边界条件缺失、角色或权限不清、不可测试描述以及潜在的运营异常，从而降低需求理解不一致和后期返工的风险。

项目当前材料显示，系统面向的核心任务是：用户输入需求文本，或上传 DOCX、文字型 PDF 文件；系统解析需求内容后生成结构化审查报告。报告包含总体风险等级、问题类型、原文引用、问题解释、缺失条件、待确认问题、可测试验收标准、相关角色和返工风险等信息。

本次选题来源于一次面向实际系统使用者的对话访谈。访谈对象为学生用户，访谈时间为 2026 年 9 月 22 日，访谈方式为当前对话访谈，访谈主题为需求歧义审查器的使用问题和功能需求。访谈原始回答已由受访者在本报告整理前直接提供，属于本项目的需求来源证据。

访谈记录摘要如下：

- 受访者身份：学生。
- 当前需求分析方式：通常先把自己作为系统使用者，检查需求是否能够覆盖自己的使用需要，并判断是否还有需求没有写入需求分析。
- 主要困难：在实际项目中很难找到足够数量的目标用户进行采访，导致需求来源不够充分；例如进行校园二手交易平台需求分析时，主要依据个人生活经历，外部需求来源较少。
- 造成影响：需求可能在后期反复修改，测试人员难以据此完成验收，后期改动成本增加。
- 对本系统的优先期待：对项目需求进行完整性分析，检查需求是否能够满足绝大部分用户。
- 对审查结果的要求：结果至少应包含原文引用、问题位置、修改建议、验收条件和风险等级。

问题可表述为：面向需要编写或评审软件需求的学生、开发者和需求人员，在课程作业或项目需求整理过程中，需求文本经常出现“尽快”“方便”“合理”等缺少量化口径的表达，也可能缺少角色权限、异常处理、输入输出和验收条件。尤其对于缺少目标用户访谈机会的学生，需求分析容易过度依赖个人经历，难以判断需求是否覆盖大多数目标用户。用户目前可能依靠自我代入、反复沟通或开发阶段才发现问题，容易造成理解偏差、验收争议和返工。拟通过需求文本解析与 AI 辅助审查，把需求完整性、歧义和验收风险整理为可定位、可修改、可验证的检查结果。

项目的一句话核心价值是：**在需求进入开发前，把文本中的不确定性转换成带原文依据、待确认问题和验收标准的结构化检查清单。**

使用前后的可观察变化是：使用前，需求问题分散在原文中，用户需要人工寻找；使用后，系统展示风险等级和问题清单，并为每个问题提供原文引用、缺失条件、确认问题和验收建议。该变化需要通过实际运行截图或完整输入输出样例进一步证明，证据为【待补充】。

### 3.2 对应 2.2：用户画像与典型场景

#### 3.2.1 主要用户

主要用户为需要编写、检查或修改软件需求的学生、个人开发者和需求人员。

- 目标：在开发前发现需求中的歧义、缺少条件和验收风险。
- 能力：能够编写或整理需求文本，能阅读结构化审查结果，并能对待确认问题进行人工判断。
- 使用环境：浏览器访问前端页面，后端在本地或可访问的服务环境中运行；输入内容可以直接粘贴，也可以来自 DOCX 或文字型 PDF 文件。
- 约束：课程项目时间有限，用户通常缺少专门的需求分析工具；AI 服务可能受网络、模型配置和返回格式影响；需求文本可能包含不适合上传到外部服务的内容。
- 痛点：模糊词语、边界条件、权限范围和异常流程容易被遗漏；仅查看一段长文本时，问题位置和验收口径不容易快速定位。

次要用户为需求评审者、测试人员或教师。他们可以利用审查报告查看待确认问题和验收条件，但当前项目未实现登录、多用户协作和权限隔离，因此不能把次要用户描述为已具备独立账户和协同能力的正式用户。

#### 3.2.2 正常场景

**场景1：直接输入需求并发起审查**

用户进入审查页面，在文本框粘贴需求，选择审查模式并点击“开始审查”。系统校验文本非空后提交请求，返回结构化报告并切换到结果页。结果页显示风险等级、问题数量和问题详情。实际执行截图：【待补充】。

**场景2：上传 DOCX 文件**

用户选择 DOCX 文件上传。后端使用 Apache POI 提取文档段落文本，前端将解析出的文本显示在需求输入区，用户可以检查或修改文本后再发起审查。实际使用的文件名、解析字符数和截图：【待补充】。

**场景3：上传文字型 PDF 文件**

用户上传包含可提取文字的 PDF。后端使用 PDFBox 提取文字并返回前端，用户确认解析结果后发起审查。实际使用的文件和解析结果：【待补充】。

**场景4：查看历史、详情并继续追问**

用户完成一次审查后进入历史记录页面，选择某条记录查看详情；如果需要进一步澄清，可以提交追问，系统将原需求和追问一起交给审查服务并保存新的结果版本。实际操作的追问内容、原版本和新版本截图：【待补充】。

**异常场景1：输入为空**

用户未输入文本就点击审查。前端应阻止提交并提示“请先输入或上传需求文本”；后端也会对空文本进行校验。实际测试结果：【待补充】。

### 3.4 对应 2.4：用户故事、需求与验收条件

#### 3.4.1 用户故事

以下用户故事均采用“作为……我希望……以便……”格式，并按照主要用户、评审/测试相关用户和系统外部服务使用者的责任进行划分。

**US-01 需求输入**

作为需求编写学生，我希望直接粘贴需求文本或上传 DOCX、文字型 PDF 文件，以便快速提交已有需求材料进行检查，而不必重新手工录入。

**US-02 需求完整性分析**

作为需求编写学生，我希望系统检查需求是否覆盖主要用户的目标、使用场景、功能、异常情况和验收条件，以便在缺少外部用户访谈时发现可能遗漏的需求。

**US-03 歧义和边界识别**

作为需求编写学生，我希望系统识别模糊表达、缺失边界、角色权限和异常处理问题，以便减少因为需求理解不一致而产生的返工。

**US-04 原文定位**

作为需求编写学生，我希望每个审查问题都包含原文引用和问题位置，以便回到需求原文核对上下文并准确修改。

**US-05 修改建议和验收条件**

作为需求编写学生，我希望每个问题都给出缺失条件、修改方向和可测试验收条件，以便将需求修改为开发人员能够实现、测试人员能够验收的描述。

**US-06 风险判断**

作为需求编写学生，我希望系统为审查结果和具体问题标记风险等级，以便优先处理可能导致较大返工的高风险问题。

**US-07 历史查看**

作为需求编写学生，我希望保存每次审查的历史记录并查看详情，以便回顾需求分析过程和已经发现的问题。

**US-08 追问和版本**

作为需求编写学生，我希望针对审查报告继续追问并生成新版本，以便在补充需求信息后重新确认问题是否已经减少。

**US-09 异常反馈**

作为需求编写学生，我希望在输入为空、文件格式不支持或 AI 服务失败时看到明确的错误提示，以便知道下一步如何修改输入或切换审查方式。

**US-10 人工确认**

作为需求评审者或测试人员，我希望看到需要人工确认的权限、业务规则和安全问题，以便不把 AI 生成的分析结果直接当作最终需求结论。

**US-11 Mock 降级**

作为无法使用外部模型服务的项目使用者，我希望系统可以使用 Mock 模式完成基础审查流程，以便在没有 API Key 或网络不稳定时仍能验证软件交互；同时我希望系统明确说明 Mock 结果不能替代真实模型判断。

### 3.5 对应 2.5：AI能力必要性与可行性

需求歧义审查不能完全依靠固定规则解决，因为需求文本中的问题既包含可用规则识别的词语，也包含需要结合上下文理解的隐含边界、角色关系、冲突条件和可测试性判断。例如“合理”“方便”等模糊词可以通过规则初步发现，但“管理员可以处理订单”是否缺少权限范围，需要结合角色、资源、动作和业务上下文分析；同一表达在不同项目中也可能具有不同的风险。

AI 的输入是用户输入或文件解析得到的需求文本，以及用户选择的审查模式。期望输出是固定 JSON 结构，包括 summary、riskLevel、counts 和 issues；每个 issue 至少应包含 id、type、severity、quote、location、explanation、missingConditions、questions、acceptanceCriteria、relatedRoles 和 reworkRisk。允许的错误包括：风险等级偏高或偏低、问题遗漏、个别解释不准确；不允许出现无法定位的虚假原文引用、泄露敏感信息、把未确认结论当成事实，或返回无法解析的结构。高风险权限、业务规则和安全结论需要人工确认。

数据来源主要是用户提供的需求文本、上传的 DOCX/PDF 内容和用户后续追问。模型服务可以是本地 Mock 逻辑，也可以是配置的通义千问 `qwen-plus` 云端服务。真实模型调用会产生费用，受到网络和外部服务时延影响，也存在隐私、幻觉、字段缺失和返回格式变化等风险。项目通过后端固定提示词、JSON 解析和字段校验降低格式风险，但不能消除内容判断错误。

非 AI 降级方案为：保留基于规则的 Mock 审查，针对模糊词、权限词、异常词和过短文本给出固定提示；在模型不可用时仍可演示输入、输出、历史记录和页面流程，但必须在界面或报告中明确 Mock 结果不替代真实模型判断。

**AI验收组1：模糊表达识别**

- 输入：包含“尽快”“方便”“合理”等词的需求文本。
- 期望输出：至少列出模糊表达问题，引用对应原文，并提出量化时间、阈值或完成定义的问题。
- 判定方法：人工核对引用是否来自输入，检查是否有可执行的确认问题；实际结果：【待补充】。

**AI验收组2：权限与边界确认**

- 输入：包含用户、管理员或权限描述但没有访问范围的需求文本。
- 期望输出：报告指出角色、资源归属、读写权限或登录状态缺失，并要求人工确认。
- 判定方法：检查问题类型、缺失条件和人工确认点；实际结果：【待补充】。

**AI验收组3：无法直接处理或需要人工确认**

- 输入：包含隐含业务规则、敏感数据或无法从文本确定的权限决策。
- 期望输出：系统不能擅自补全业务事实，应列出待确认问题，并保留人工确认入口或说明。
- 判定方法：由需求人员对照原文检查是否存在虚构结论；实际结果：【待补充】。

## 4. 实验小结

### 4.1 最终选题和核心流程

本实验最终选题为“AI需求歧义审查器”。项目面向需求编写者、个人开发者、测试人员和需求评审者，围绕一条核心流程展开：用户输入或上传需求文本，系统解析文本并进行 AI/Mock 审查，生成包含风险等级、问题类型、原文引用、缺失条件、待确认问题、可测试验收标准和返工风险的结构化报告；用户还可以查看历史、删除记录并继续追问生成新版本。

### 4.2 MVP边界和AI必要性

MVP 聚焦需求文本审查，不扩展到扫描 PDF OCR、登录、多用户协作、支付、MCP和生产级安全治理。AI 的价值在于辅助理解自然语言上下文、识别隐含边界、生成澄清问题和可测试验收标准；固定规则适合识别部分关键词和完成流程降级，但难以覆盖不同业务场景下的上下文关系。因此项目保留 Mock 规则模式用于流程演示，同时允许接入通义千问；所有高风险结论和业务规则仍需要人工确认。

### 4.3 需求变化、删减或取舍

本次分析中的一项重要取舍是：将项目核心范围收敛为“需求输入或上传—AI审查—结构化报告—追问确认”，明确不在本学期实现登录、多用户协作、支付、MCP和扫描 PDF OCR。取舍原因是这些功能会增加身份、权限、部署、第三方服务和数据安全等复杂度，不能直接提升当前核心用户流程的需求审查价值。另一个取舍是保留 Mock 模式作为非 AI 降级方案，以便在没有 API Key、网络不稳定或模型服务不可用时仍可演示软件流程，但不把 Mock 输出当成真实 AI 效果结论。

本次需求变化的实际发生时间、原始版本和对应 Commit 为【待补充】。如果没有保存版本差异，应说明“项目材料未提供可核验的多版本需求记录，以上为根据当前实现整理的范围取舍，不将其描述为有完整版本证据的迭代结论”。

### 4.4 实验结论和证据边界

根据项目 README 和源代码，可以确认系统的主要技术栈和设计范围：前端采用 Vue 3、Vite、TypeScript 和 Element Plus，后端采用 Spring Boot 3 和 Java 17，使用 H2 文件数据库；系统支持 DOCX 和文字型 PDF 文本提取，提供 Mock 和可选通义千问审查模式，并具备结构化结果展示、历史记录、详情、删除和追问版本等功能。

但是，当前 TEST2 目录没有现成报告模板、实际输入输出样例、完整测试日志或 Git 提交记录。虽然已经补充了对话访谈记录、项目启动截图和用例图，但这些材料不能替代输入文件、审查结果、异常测试和版本证据。因此，本文不能填写未经测量的准确率、成功率、响应时间或稳定性指标，也不能把源代码中存在的接口直接当作本次实验已经通过的现场验收。相关内容应使用真实输入输出、日志和仓库版本记录继续补充。
