# 需求规格书

**项目名称：AI 需求歧义审查器**  
**文档版本：V1.1（测试修订版需求分析）**  
**文档状态：用于实验四“测试修订版”的实现、测试与验收**  
**编写依据：现有可运行初版代码、README、前后端接口及实验四报告要求**

## 1. 文档目的

本文档定义 AI 需求歧义审查器测试修订版的用户需求、功能边界、数据规则、接口契约、异常处理、非功能指标和验收标准。它同时作为：

- 测试修订版的开发依据；
- 测试用例和缺陷修复的依据；
- 实验四报告中“需求分析、核心业务闭环、测试与复测”的引用依据；
- AI 生成代码人工审查的判断基线。

本文档中的“必须”表示测试修订版的验收条件；“建议”表示后续迭代内容。

## 2. 产品定位与目标

### 2.1 产品定位

系统面向产品经理、开发人员、测试人员和课程实验使用者。用户输入一段软件需求，或上传 Word/PDF 文档，系统识别其中的模糊表达、边界缺失、角色权限问题、不可测试描述、矛盾、安全和运营异常风险，生成带原文引用的结构化审查报告。

### 2.2 产品目标

1. 把自然语言需求转换为可讨论、可确认、可测试的问题清单。
2. 对每个问题给出风险级别、原文位置、缺失条件、待确认问题和验收标准。
3. 支持用户围绕同一份报告继续追问，并保留审查版本。
4. 允许用户回看和删除本地历史记录。
5. 在 AI 服务不可用或未配置密钥时，仍可通过 Mock 模式演示完整业务流程。
6. 对输入、文件、模型输出和持久化失败给出可理解的反馈，避免页面无响应或后端直接崩溃。

## 3. 用户角色与典型场景

| 角色 | 目标 | 主要操作 |
|---|---|---|
| 需求提出者/产品经理 | 发现需求中的歧义和遗漏 | 粘贴需求、上传文件、查看问题、回答追问 |
| 开发人员 | 判断实现边界和返工风险 | 查看引用、缺失条件、接口/边界问题和相关角色 |
| 测试人员 | 获得可执行的验收口径 | 查看并复制验收标准，检查正常和异常场景 |
| 课程实验使用者 | 演示完整闭环并保留证据 | 使用 Mock 模式审查、追问、查看历史和删除记录 |
| 系统维护者 | 配置 AI 和运行环境 | 配置 AI_MODE、API Key、模型和服务地址 |

### 3.1 核心用户故事

> 作为需求提出者，我希望粘贴一段需求或上传 `.docx`/文字型 `.pdf`，选择审查模式后获得带原文引用和风险分级的审查报告；当我对问题有疑问时，可以继续追问并查看新版本；审查记录可以在历史页重新打开或删除。

## 4. 当前初版基线与修订范围

### 4.1 初版已具备能力

- Vue 3 + TypeScript + Element Plus 页面；
- Spring Boot 3 + Java 17 REST 后端；
- 文本输入和 `.docx`、文字型 `.pdf` 解析；
- 全面审查、可测试性、安全与权限三种模式入口；
- Mock 审查和可选的通义千问兼容接口调用；
- 审查报告包含 summary、riskLevel、counts、issues；
- 问题字段包含原文引用、位置、解释、缺失条件、问题、验收标准、角色、返工风险；
- 追问并保存历史版本；
- H2 文件数据库保存记录；
- 历史列表、详情查看和删除。

### 4.2 测试修订版重点补全

测试修订版必须围绕初版实际暴露的风险补全以下内容：

1. 对空白文本、超长文本、非法请求体进行明确校验；
2. 对上传文件扩展名、大小、空文件、解析失败进行统一处理；
3. 对 AI 返回缺字段、错误枚举、非法 JSON 和外部服务超时进行安全降级或明确报错；
4. 确保风险计数与问题明细一致，且报告结构稳定；
5. 追问时校验记录存在、问题非空，并保证旧版本和新版本不丢失；
6. 查询、删除不存在的记录时返回明确结果；
7. 前端对加载中、空数据、错误输入、服务失败和无历史记录提供可理解反馈；
8. 为关键操作记录必要日志，便于定位问题；
9. 保持 Mock 模式下的完整可演示性，不把 API Key 暴露给浏览器。

## 5. 功能需求

### 5.1 需求输入

#### FR-INPUT-001 文本输入

系统必须提供多行文本框，允许用户直接粘贴或编辑需求原文。

- 文本不能为空或仅包含空白字符；
- 文本最大长度为 20,000 个字符；
- 页面显示当前字数和最大字数；
- 超过上限时禁止开始审查，并提示具体限制；
- 原文在生成报告后必须可回看，不能被系统静默改写。

#### FR-INPUT-002 文件上传

系统必须支持 `.docx` 和文字型 `.pdf` 文件上传并提取文本。

- 单文件最大 10 MB；
- 文件为空、扩展名不支持、内容无法解析时必须返回明确错误；
- 解析成功后显示文件名、提取字符数和可编辑文本；
- 上传解析不应自动开始 AI 审查，用户必须主动点击“开始审查”；
- PDF 扫描图片没有可提取文字时，应提示“仅支持文字型 PDF”，不得生成空报告；
- 上传内容不得把 API Key 或服务器内部路径返回给前端。

#### FR-INPUT-003 审查模式

系统必须支持以下模式，并将模式保存到审查记录：

| 模式 | 关注点 |
|---|---|
| 全面审查 | 模糊、边界、权限、测试、安全、运营等全部问题 |
| 可测试性 | 输入、输出、边界、验收和异常场景 |
| 安全与权限 | 身份、角色、资源访问、敏感信息和安全边界 |

未知模式必须被拒绝或降级为“全面审查”，且行为需要在接口文档中固定。

### 5.2 审查处理

#### FR-REVIEW-001 开始审查

用户点击开始审查后，系统必须：

1. 校验文本和审查模式；
2. 调用 Mock 规则或已配置的 AI 服务；
3. 校验模型输出结构；
4. 生成审查报告；
5. 保存原文、模式、报告和创建时间；
6. 返回可在结果页展示的记录。

同一输入重复审查可以生成不同历史记录，不得覆盖已有记录。

#### FR-REVIEW-002 报告结构

报告必须包含以下字段：

```json
{
  "summary": "总体结论",
  "riskLevel": "high|medium|low",
  "counts": {"high": 0, "medium": 0, "low": 0},
  "issues": []
}
```

每个 `issue` 必须包含：

- `id`：问题唯一标识；
- `type`：`ambiguous_term`、`missing_boundary`、`conflict`、`permission`、`testability`、`security` 或 `operational`；
- `severity`：`high`、`medium` 或 `low`；
- `quote`：需求原文引用；
- `location`：段落、行号或“全文”等位置说明；
- `explanation`：问题解释；
- `missingConditions`：缺失条件数组；
- `questions`：待确认问题数组；
- `acceptanceCriteria`：可测试验收标准数组；
- `relatedRoles`：相关角色数组；
- `reworkRisk`：返工风险说明。

系统必须保证 `counts` 与 `issues[].severity` 的实际数量一致；无问题时 `issues` 为空数组，风险等级为 `low`，页面显示明确的无明显问题状态。

#### FR-REVIEW-003 原文引用

每个问题必须尽量引用输入原文并给出位置。无法定位时可以使用“全文”，但不得伪造不存在的原文。原文引用不得脱离当前审查文本。

#### FR-REVIEW-004 AI 与 Mock 模式

- 默认 Mock 模式必须不依赖 API Key，且可完成审查和保存；
- Qwen 模式仅由后端调用外部服务；
- API Key 只能从环境变量或后端配置读取，不得进入前端代码、接口响应或日志；
- AI 服务超时、网络失败、返回非法 JSON 或字段不符合契约时，系统必须返回可理解错误并记录原因；
- 模型原始响应不得直接作为未经校验的 HTML 或脚本渲染。

### 5.3 报告查看与筛选

#### FR-REPORT-001 结果页

结果页必须展示：

- 总体风险等级和摘要；
- 高、中、低风险数量；
- 问题类型筛选；
- 每个问题的原文引用、位置、解释、缺失条件、待确认问题、验收标准、相关角色和返工风险；
- 当前审查时间和模式；
- 继续追问入口；
- 返回编辑和重新审查入口。

#### FR-REPORT-002 空状态和错误反馈

- 当前筛选没有问题时显示空状态；
- 报告为空或字段异常时显示“报告格式错误/无法展示”，不得出现空白页面；
- 请求进行中时按钮显示加载状态并防止重复提交；
- 网络失败时显示可理解的错误提示，并允许用户重试。

### 5.4 追问与版本

#### FR-FOLLOW-001 追问

用户可以对已有报告提交追问。

- 追问不能为空或仅包含空白字符；
- 追问长度建议限制为 2,000 个字符；
- 记录不存在时返回明确的“审查记录不存在”；
- 追问必须基于原文和当前模式生成新报告；
- 追问成功后结果页显示新报告。

#### FR-FOLLOW-002 版本保留

每次追问前的报告必须保存到 `versions`，新报告成为当前报告。保存失败时不得只更新一部分数据。版本至少应能够说明生成顺序和时间；旧版本不能被静默删除。

### 5.5 历史记录

#### FR-HISTORY-001 列表与详情

历史页按创建时间倒序展示记录摘要、时间、风险等级及高/中/低数量。用户可以打开详情并看到原文、当前报告和历史版本。

#### FR-HISTORY-002 删除

用户删除记录前必须二次确认。删除成功后从列表移除；删除不存在的 ID 时返回明确结果，不得导致未处理异常。删除失败时保留列表并显示错误。

#### FR-HISTORY-003 数据初始化与恢复

后端首次运行时自动创建 H2 文件数据库和表结构。系统应提供用于测试的样例需求文本，测试人员可以通过重新初始化或清理数据恢复空数据状态。生产性数据清理操作必须避免误删全部记录。

## 6. 数据与接口规格

### 6.1 核心数据实体

| 字段 | 类型 | 规则 |
|---|---|---|
| id | UUID | 系统生成，唯一且不可修改 |
| text | TEXT | 必填，1—20,000 字符 |
| mode | VARCHAR | 三种审查模式之一 |
| createdAt | Instant | 服务端生成，不接受前端伪造 |
| reportJson | TEXT | 经结构校验的当前报告 |
| versionsJson | TEXT | 按顺序保存的历史报告数组 |

### 6.2 接口契约

| 方法 | 路径 | 输入 | 成功结果 | 主要错误 |
|---|---|---|---|---|
| POST | `/api/reviews` | `{text, mode}` | `ReviewResponse` | 400 参数错误、502 AI失败、500保存失败 |
| POST | `/api/reviews/upload` | multipart `file` | `{fileName,text,characters}` | 400 类型/内容错误、413 超限 |
| POST | `/api/reviews/{id}/follow-up` | `{question}` | 更新后的 `ReviewResponse` | 400 空问题、404不存在、502 AI失败 |
| GET | `/api/reviews` | 无 | `HistoryItem[]` | 500读取失败 |
| GET | `/api/reviews/{id}` | UUID | `ReviewResponse` | 400 ID格式错误、404不存在 |
| DELETE | `/api/reviews/{id}` | UUID | 204 | 404不存在、500删除失败 |

接口错误响应至少包含：

```json
{"error":"面向用户的错误说明","code":"可选错误码"}
```

错误信息不得包含 API Key、完整堆栈、数据库连接字符串或本机绝对路径。

## 7. 非功能需求

### 7.1 可用性

- 在 README 指定命令启动后，前端和后端能够正常访问；
- Mock 模式下，常规文本审查响应时间目标不超过 10 秒；
- 操作过程必须显示加载状态；
- 页面在桌面宽度和窄屏下都可完成核心操作。

### 7.2 可靠性

- 单次请求失败不能导致后端进程退出；
- 数据库读取失败、AI 调用失败、文件解析失败均有日志和用户反馈；
- 重复点击开始审查不会在一次页面操作中发送重复请求；
- 保存报告失败时不产生半条历史记录。

### 7.3 安全性与隐私

- API Key 只存在后端配置；
- 上传文件仅用于当前解析流程，不在页面中执行其内容；
- 报告内容按文本渲染，防止需求原文中的 HTML/脚本被执行；
- 对文件类型、大小和文本长度进行服务端校验，不能只依赖前端；
- 日志不得记录完整 API Key；
- 当前版本为单机本地原型，不承诺多用户隔离、登录、协作和生产级权限控制。

### 7.4 可维护性

后端按 Controller、Service、Repository、Entity/DTO 组织；前端按页面、组件、接口调用和状态组织。关键校验和错误处理应有清晰方法边界，避免把全部业务逻辑堆在控制器中。

## 8. 业务流程与验收条件

### 8.1 正常业务闭环

```text
输入需求/上传文件
→ 解析并确认文本
→ 选择审查模式
→ 开始审查
→ AI/Mock分析
→ 校验报告结构
→ 保存审查记录
→ 展示风险和问题
→ 用户追问
→ 保存旧版本并展示新版本
→ 历史页查看或删除
```

验收条件：使用一段包含“尽快”“方便”“谁可以查看”等真实业务语义的需求，系统能够返回至少一个带引用、风险等级、待确认问题和验收标准的问题，并在历史页重新打开。

### 8.2 异常业务闭环

1. 空文本：禁止提交并提示输入需求文本；
2. 超长文本：禁止提交并提示长度限制；
3. 不支持格式：上传失败并说明支持的格式；
4. 空文件或扫描 PDF：提示无法提取文字；
5. 不存在记录：详情和追问返回 404 语义错误；
6. AI 返回错误：页面显示失败原因，历史中不保存无效报告；
7. 无历史数据：历史页显示空状态；
8. 空筛选结果：结果页显示筛选空状态；
9. 重复点击：只产生一次请求和一条记录。

## 9. 测试修订版验收用例

| 编号 | 场景 | 输入/操作 | 预期结果 |
|---|---|---|---|
| TC-01 | 正常文本审查 | 输入含模糊词和权限缺口的需求，选择全面审查 | 返回报告并保存历史，高风险问题可见 |
| TC-02 | 空文本 | 输入空格后点击审查 | 前端和后端均拒绝，提示需求不能为空 |
| TC-03 | 超长文本 | 提交超过 20,000 字符 | 禁止提交或返回明确长度错误 |
| TC-04 | 正常 DOCX | 上传可读 Word | 返回提取文本和字符数，不自动审查 |
| TC-05 | 非法文件 | 上传 `.txt`/空文件/扫描 PDF | 返回明确类型或无法提取错误 |
| TC-06 | 空数据结果 | 使用没有风险词的完整需求或筛选无匹配类型 | 显示低风险/筛选空状态，不白屏 |
| TC-07 | 错误输入 | 追问为空或只含空格 | 不发请求，显示追问不能为空 |
| TC-08 | 不存在记录 | 使用随机 UUID 查询、追问或删除 | 返回记录不存在，不产生服务器异常页面 |
| TC-09 | 追问版本 | 对已有报告提交有效追问 | 新报告成为当前报告，旧报告保存在 versions |
| TC-10 | AI 输出异常 | Mock 测试桩或服务返回缺字段/非法 JSON | 返回可理解错误，数据库不保存无效报告 |
| TC-11 | 历史与删除 | 创建两条记录，查看详情后删除一条 | 列表倒序，删除后仅剩另一条 |
| TC-12 | 重复提交 | 快速连续点击开始审查 | 页面只发送一次有效提交，数据不重复 |

## 10. 日志与可观测性要求

关键操作至少记录以下信息：

- 时间、日志级别和操作名称；
- 请求路径和审查记录 ID（如已生成）；
- 上传文件扩展名、大小和解析结果；
- AI 模式、耗时和成功/失败状态；
- 报告校验失败原因；
- 数据库保存、查询、追问和删除结果。

日志不得记录完整需求中的敏感内容、API Key 或完整外部响应。日志位置应在运行说明中明确，例如 `backend/logs/application.log` 或控制台输出。

## 12. 明确不在本次范围内

以下内容不作为测试修订版必须实现的功能：

- 用户注册、登录和多用户数据隔离；
- 团队协作、评论、审批和权限管理后台；
- OCR 扫描 PDF；
- 在线导出 Word/PDF 报告；
- 支付、配额和计费；
- MCP 接入和多模型编排；
- 生产环境级别的限流、审计和高可用部署。

## 13. 完成定义

测试修订版满足以下条件后，视为需求完成：
